# anydoc 转换案例库（case-library）

本案例库收录任意文档转 Markdown 的典型处置场景，供同类任务套用。
每则案例按「场景 / 处理 / 结论 / 要点」四段呈现；套用时须按实际文件复核，
凡未能实测确认的数值与文件名，一律标注【待核】。命名与结构一律以本案例库为准。

---

## 案例一　合同批量入库前统一转 Markdown

- **场景**：项目公司要把一批 Word 版合同（【待核：实际份数】）放进知识库，要求统一转成 Markdown 并保持一一对应。
- **处理**：先 `ls` 清点源文件数与扩展名，再逐份 `npx -y @firecrawl/anydoc "<file>" -o "<stem>.md"`；转换后跑 `python3 scripts/anydoc_check.py --source ./合同 --md-dir ./合同_md` 做缺件/空件/结构三项对账。
- **结论**：交付同名 `.md` 集合与质检报告（成功数、失败数、失败原因单列），不做内容增删改写。
- **要点**：①产物命名沿用源文件名干，便于回溯；②大文件先 `-o` 落盘再抽读，避免全文灌入上下文；③质检不通过不得直接入库。

## 案例二　扫描件 PDF 被误当文字层 PDF

- **场景**：用户上传一份扫描版合同 PDF，要求直接转 Markdown 做条款检索。
- **处理**：转换退出码为 1（或产物仅含空白/极短文本），触发失败模式 F1；判定为无文字层，**不重复重试**同一条命令，按冗余路径改走 textin-xparse 做 OCR 取得文字层，再回归 anydoc 或直接使用 OCR 产出的 Markdown。
- **结论**：先分流到 OCR 环节，再回到转换流程；向用户说明该 PDF 属扫描件，转换器本身不支持 OCR。
- **要点**：①首页能否选中文字是判断题；②「不适用」即拒，不做无效重试；③降级不等于失败，是换正确工具。

## 案例三　大文档全文灌入上下文导致截断

- **场景**：一份 300 页 PDF 报告，用户要求读要点，直接 stdout 转换导致输出被截断、关键章节丢失。
- **处理**：改为 `-o /tmp/report.md` 落盘，再用检索/分片读取定位目标章节；必要时按目录切片后逐段提炼。
- **结论**：交付「要点 + 来源章节」；说明因体量原因采用落盘分片读取，未全文进上下文。
- **要点**：①黄金窗口为单文件 ≤50 页/≤10MB；②落盘是默认路径不是例外；③结论须回指原文章节。

## 案例四　环境缺失（npx / Node 不可用）时的降级

- **场景**：沙箱内无 Node 20+ 或无法访问 npm 源，`npx` 命令不可用。
- **处理**：触发失败模式 F5，**回退到备用解析路径**——有文字层的 PDF 走平台自带文档解析或 `pdftotext` 兜底，Office 文档转 textin-xparse 或 ima-doc 读取；同时给出安装 Node 20+ 的补救说明。
- **结论**：产出可读文本并在交付说明中标注所用替代通道与精度差异。
- **要点**：①先看失败分支再换工具；②兜底通道须在交付物中如实标注；③不隐去降级事实。

## 案例五　转换产物质检不通过（表格错位 / 乱码）

- **场景**：源文件使用复杂合并单元格，转换后 Markdown 表格列错位；另有 GBK 老文件转换出现乱码。
- **处理**：表格错位 → 人工核对源表结构后重建关键表；乱码 → 判定为源文件编码问题，先用 text-io 的 `convert` 转 UTF-8 后重新转换。质检由 `anydoc_check.py` 复跑确认。
- **结论**：两者分别以「人工补表 + 编码前置修复」闭环，复跑质检合格后交付。
- **要点**：①结构类问题机器难全自动还原，须标注待核；②编码问题在入口解决，不在出口补救；③断点续跑只跑失败件，不重跑已合格件。

---

**共同纪律**：全部案例遵循「不编造原文没有的内容、不删除原文结构、不把质检前产物当交付物」三条底线；
涉及用户文档的，一律本地处理，文件不出本机。
