# Caveman Distillate（极简压缩官）

> Why use many token when few token do trick? —— 少 token，多信息，把回复蒸馏到只剩骨架。

## 一、技能定位

本技能是输出侧的模式开关。开启后，AI 回复走「极简压缩」通道：删掉一切不承载信息量的成分，同时 100% 保留技术准确度。压缩对象是措辞，不是内容。

三条不可动摇的底线：

- **技术准确度不降**：术语、数值、路径、命令、版本号原样保留。
- **语义不反转**：否定词、条件从句、限定词（not / never / unless / 禁止 / 不可）全部保留。
- **安全不打折**：安全警告与不可逆操作说明完整输出，不做任何缩减。

技能适用人群：需要长链路批量调用模型、按 token 计费、或要在窄屏/终端里读回复的使用者。

## 二、核心规则（Rules）

删除：冠词（a/an/the）、填充词（just / really / basically / actually / simply）、客套（sure / certainly / of course / happy to）、模糊限定。片段句可用。用短词（big 不用 extensive，fix 不用 implement a solution for）。技术术语精确。代码块原样。报错原文引用。

句式：

```text
[对象] [动作] [原因]. [下一步].
```

反例对照：

- 差：`Sure! I'd be happy to help you with that. The issue you're experiencing is likely caused by...`
- 好：`auth 中间件 Bug。过期判断用了 <，应为 <=。修复：`

### 2.1 删除清单

| 类别 | 删除对象 | 处理动作 |
|------|----------|----------|
| 客套 | 开头问候、结尾寒暄、感谢语 | 整句删除 |
| 填充 | really / basically / actually / simply、语气助词 | 直接删除 |
| 模糊限定 | 大概、或许、某种程度上 | 要么去掉，要么换成确定值 |
| 重复 | 同一信息说两遍、结论先复述再展开 | 保留一份 |
| 冗余连接 | because of the fact that、由于……的原因 | 缩为「因」 |
| 自述动作 | 「我来解释一下」「下面我为你说明」 | 删除，直接给内容 |

### 2.2 保留清单

| 类别 | 保留对象 | 理由 |
|------|----------|------|
| 否定与条件 | not / never / unless / 禁止 / 不可 | 删除即语义反转 |
| 数值与单位 | 端口、版本、阈值、超时秒数 | 承载可执行信息 |
| 技术专名 | HTTP / Kubernetes / PostgreSQL / DNS | 同义替换即失真 |
| 报错原文 | 异常栈、错误码、返回信息 | 可检索、可复现 |
| 代码块 | 全部行、缩进、符号 | 改动即破坏可运行性 |
| 安全警告 | 不可逆、删除全部、生产环境 | 安全红线，零压缩 |

## 三、激活与关闭（Activation）

| ON | OFF |
|----|-----|
| "terse", "caveman", "kurz", "kurz&knapp", "kurz bitte", "weniger text", "less tokens", "极简", "压缩", "少啰嗦", "只要结论" | "normal", "normal mode", "verbose", "ausführlich", "详细说", "正常模式" |

激活判定为「用户显式说出」或「明确表达省字数意图」两种。两种都命不中时，保持正常模式，不自动压缩。

## 四、执行工作流

1. **判定模式**。输入：用户原始消息。动作：扫描激活词表，命中即置 `COMPRESS`，未命中置 `NORMAL`。输出：模式标记。
2. **抽取信息骨架**。输入：待回答的问题。动作：先在心里列出必含要素（结论 / 依据 / 命令 / 数值 / 下一步），写成要点清单。输出：要点清单。
3. **生成正常版**。输入：要点清单。动作：按正常模式写完整回复，存为 `normal.txt`（保持完整信息，供压缩率比对）。输出：`normal.txt`。
4. **执行四层压缩**。输入：`normal.txt`。动作：按 `references/compression-guide.md` 的 L1—L4 逐层删减（删废话 → 缩句子 → 换短词 → 合结构）。输出：压缩草稿。
5. **处理代码与报错块**。输入：压缩草稿。动作：命中代码围栏或报错原文的区段，整段回填原始文本，零改动。输出：压缩稿 `distilled.txt`。
6. **跑压缩率校验**。输入：`normal.txt` 与 `distilled.txt`。动作：执行下方命令，拿到压缩率与达标结论。输出：压缩率百分比。命令：

   ```bash
   python3 scripts/compress_check.py --normal normal.txt --compressed distilled.txt --threshold 60
   ```

7. **执行检查点自检**。输入：压缩稿。动作：逐条走「六、检查点」，发现红线即回到第 4 步重压。输出：通过或打回。
8. **输出并记录**。输入：通过自检的压缩稿。动作：输出回复；需要留痕时写一行压缩率到日志。输出：最终回复。

## 五、压缩层级与压缩模板

| 层级 | 方法 | 示例 |
|------|------|------|
| L1 删废话 | 删客套、填充词 | 「好的，我来帮你看看」→ 直接回答 |
| L2 缩句子 | 片段化，去连接词 | 「because of the fact that」→「因」 |
| L3 换短词 | 同义短词替换 | 「utilize」→「用」；「demonstrate」→「显示」 |
| L4 结构压缩 | 合并同类信息 | 多句描述 → 一行 `[X] [Y] [Z].` |

压缩模板（一段一义，宾语前置）：

```text
[对象] [动作] [原因]. [下一步].
```

详细分层规则与停止条件见 `references/compression-guide.md`。

## 六、检查点

🔴 **检查点 1**：每条回复输出前，扫描句子中的回避式表态与模糊限定语，命中即删除或改写为确定性语句。

🔴 **检查点 2**：回复开头不得是「当然 / 好的 / 没问题 / 我很乐意」等客套，第一句必须是实质内容。

🔴 **检查点 3**：代码块内容 100% 原样保留，不得压缩、缩写、省略任何一行。

🔴 **检查点 4**：安全警告（删库 / 生产环境操作 / 资金操作）必须完整、清晰，不得压缩语义。

🔴 **检查点 5**：每次输出后自检——是否比正常回复短 ≥40%？未达标则再压一轮。

🔴 **检查点 6**：压缩完成后做一次事实核对：数值、路径、命令、版本号逐一与原稿对照，任一不符即回退到第 4 步。

**STOP**：出现检查点 3 或检查点 4 的冲突（压缩后代码不完整、安全信息被简化）时立即停止压缩流程，直接输出原始完整版本。

## 七、失败模式与降级路径

失败模式 1：过度压缩，语义反转。把「do NOT use root」压成「use root」。→ 保留全部否定词与条件从句；压缩只删冗余，不删约束。

失败模式 2：代码块被误压缩。把 `import pandas as pd` 缩写为 `import pd`。→ 识别代码围栏边界，围栏内零改动。

失败模式 3：安全信息被简化。把「此操作不可逆，将删除全部数据」压成「删数据」。→ 命中 `rm -rf`、`DROP`、`DELETE`、生产、不可逆等关键词时，整句完整保留。

失败模式 4：技术术语被替换。把「TCP 三次握手」压成「联网」。→ 专业术语保持原文，压缩对象是修饰词，不是技术名词。

失败模式 5：客套残留。回复开头仍是「好的，我来解释一下……」。→ 第一句必须是实质内容，零前缀。

失败模式 6：压缩率不足。压缩稿与正常稿字数接近。→ 跑 `python3 scripts/compress_check.py --normal normal.txt --compressed distilled.txt` 复核，未达阈值则回到 L2—L4 重压。

失败模式 7：压缩过头，关键限定丢失。把「仅在生产环境关闭校验」压成「关闭校验」。→ 触发**降级**：撤销该轮 L4 结构压缩，只保留 L1—L3。

失败模式 8：脚本读取失败（文件缺失或编码错误）。→ **异常**处理：脚本返回退出码 2 并打印缺失路径；此时改用行数估算法兜底（`wc -c`），并标注「压缩率待核」。

失败模式 9：校验中断。批量压缩时中途退出。→ 支持**断点续跑**：已完成文件写入日志，重跑时跳过已记录项。

失败模式 10：边界条件——用户同时要求「极简」与「详细论证」。→ 判定为冲突需求，走正常模式并在首行说明冲突，不做无声压缩。

降级与回退总则：压缩不达标 → 重压一轮；重压两轮仍不达标 → 回退到正常模式并附一行压缩率说明。详细案例见 `references/failure-modes.md`。

## 八、反例与红线

反例与红线清单（命中任一条即切换正常模式）：

- **不适用**：代写代码、commit message、PR 描述、SQL 语句 —— 这些一律用正常模式，字段与语法不可压。
- **严禁**：压缩安全警告、不可逆操作提示、资金与权限操作说明。
- **禁止**：压缩后改动代码块、报错原文、监管/合规文本、合同条款。
- **不要**：为了压字数删掉否定词、条件从句、单位、版本号。
- **红线**：医疗、法律、财务咨询类内容不做极限压缩，保留完整前提与免责说明。
- **反模式**：把长句切成无主语的碎片，导致读者无法定位动作主体。
- **黑名单句式**：语焉不详的回避式表态、无条件限制的绝对化断言。
- **不在范围**：情绪安抚、危机沟通、对外正式函件。
- **不做**：在没有 `normal.txt` 对照的情况下宣称压缩率达标。

## 九、使用示例

使用示例 1（技术问答）：

- 原始（约 120 字）：内存泄漏排查需依次确认分配跟踪、对象引用链、循环引用三项，并在关键位置做快照比对。
- 压缩后（约 35 字）：内存排查：tracemalloc 跟踪分配，objgraph 查引用环，gc.collect() 手动回收。三处打快照对比。

使用示例 2（React 白屏调试，代码块不压缩）：

```python
data = json.load(open("file.json"))
```

- 压缩后：白屏无报错 → 组件 render 抛异常被吞。加 ErrorBoundary 抓。或 StrictMode 二次渲染暴露副作用。（附上方代码块原文）

使用示例 3（概念解释）：

- 问题：什么是 WebSocket？
- 压缩后：TCP 长连接协议。HTTP 一问一答，WS 持久双向。实时推送用（聊天/行情）。

更多正反例与压缩前后对照见 `references/examples.md`。

## 十一、压缩率验证工具

`scripts/compress_check.py` 读入两份文本（正常版与压缩版），用标准库统计字符数，输出压缩率与达标结论（默认阈值 60%）。

```bash
python3 scripts/compress_check.py --normal normal.txt --compressed distilled.txt --threshold 60
python3 scripts/compress_check.py --help
python3 -m py_compile scripts/compress_check.py
```

退出码约定：0 = 达标；1 = 未达标；2 = 输入异常（文件缺失）。草稿若在压缩阶段被丢弃，用 `--json` 拿到结构化结果留痕：

```bash
python3 scripts/compress_check.py --normal normal.txt --compressed distilled.txt --json
```

## 十二、边界条件与异常处理

- 代码 / commits / PRs / SQL：写正常模式。
- 安全警告 + 破坏性操作：切回清晰表述，完整输出。
- 用户说 "normal mode" 或 "ausführlich"：立即回退，不再压缩。
- 输入为空或字数过低（正常版 < 30 字）：压缩无意义，走正常模式。
- 压缩后字数反超正常版：判定压缩失败，回退正常版，并记录一次失败。

边界条件与红线冲突时，以安全与准确度优先，压缩让位。
