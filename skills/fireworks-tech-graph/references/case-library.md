# 案例库 · 技术图绘制官（case-library）

本文件归档经过验证的真实出图案例，覆盖架构图、序列图、ER 图与图型对照场景。
每条案例含**背景 / 做法 / 结果**，可直接作为同类请求的处置范式；案例中的业务
字段以【待核：…】占位，未核实信息不得当作已确认事实引用。

## 案例 1 · 三层微服务架构图（一次成图，风格 3 Blueprint）

- **背景**：用户需要一张用于架构说明书的微服务架构图，给出文字描述："最上面是
  用户端与定时任务，中间是网关与订单服务，最下面接 MySQL 与 Redis，用蓝图风格。"
  画布默认 `0 0 960 600`、节点标准 180×90px。
- **做法**：
  1. 归类型为「架构图」→ 套用水平分层规则，分接入层 / 服务层 / 数据层三行；
  2. 提炼层/节点/边三元结构，写入 `specs/order-arch.json`，节点全部对齐 8px 基础网格；
  3. 加载 `references/style-3-blueprint.md` 取蓝色技术风令牌（背景 `#0a1628`）；
  4. 执行 `python3 scripts/render_diagram.py --spec specs/order-arch.json --out out/order-arch-style3.svg --style 3 --width 1920 --png`；
  5. 运行 `python3 scripts/techgraph_check.py --svg out/order-arch-style3.svg --cjk` 做写入前自检。
- **结果**：SVG 五项自检一次通过，PNG 导出正常（1920px 宽，非全白），交付 SVG+PNG
  双份与风格编号。**经验**：三层以上架构图坚持先定层再定节点，可避免后续返工重排。

## 案例 2 · 下单支付时序图 · 风格切换（同规格二出图）

- **背景**：用户要求"画一张下单支付的时序图，参与者是用户、订单服务、支付网关、
  银行，然后换成暗色终端风格再出一份"。
- **做法**：
  1. 归类型为「序列图」→ 参与者为垂直生命线，消息按时间自上而下排布；
  2. 激活框用细填充矩形表示处理中，alt/loop 帧用虚线矩形框并在左上角标注；
  3. ViewBox 高度按 `80 + 消息数 × 50` 计算；
  4. 同一份规格 JSON 连续出两次图：第一版 `--style 1`（Flat Icon），第二版 `--style 2`
     （Dark Terminal，背景 `#0f0f1a`）；
  5. 因中文标签存在，两次出图均把 `'Noto Sans CJK SC'` 写入字体栈并加 `--cjk` 复核。
- **结果**：两份 SVG 风格独立、无颜色串味，交付时在文件名中标注风格编号。**经验**：
  规格复用是风格切换的正确做法；若在旧图上叠改，容易造成风格漂移（此为反模式）。

## 案例 3 · 数据库 ER 图（主外键与基数标注）

- **背景**：用户要求"把订单、订单明细、商品、客户四张表画成 ER 图，标出主外键和
  一对多关系"，用于贴进内部 Wiki。
- **做法**：
  1. 归类型为「ER 图」→ 实体矩形最小宽度 160px，主键加下划线，外键标 `(FK)`；
  2. 关系用菱形，基数标注 `1` 与 `0..*`；宽布局 ViewBox 取 `0 0 1200 600`；
  3. 风格取 4 Notion Clean（白色极简），便于贴进 Confluence 与 Notion；
  4. 规格缺字段时按 `id`、`label`、`sub` 三项最小集补齐，缺 `from`/`to` 的边丢弃。
- **结果**：一张 ER 图含 4 实体、5 关系，连线连接点取边框中点，未穿越实体内部。
  **经验**：ER 图与流程图混用时，先确认用户主图型，避免把基数字段画成流程标签。

## 案例 4 · 图型归类失败对照（反例）

- **背景**：用户描述"帮我画个系统，能实时显示当前订单量并跟着数据跳动"。
- **做法**：判读时识别出「实时数据绑定 + 动画」诉求，命中能力边界——本技能只出
  静态 SVG，不做需要实时数据绑定的动态图表（D3.js/Plotly/SMIL）。
- **结果**：先向用户说明边界，并给出替代路径（改用前端图表库或绘图软件），
  不下单出图。**经验**：边界外的请求应当先声明边界、再给替代路径，而不是硬出图。
