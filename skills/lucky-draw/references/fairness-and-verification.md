# 公平性与可验证性原理

## 一、为什么随机源的选择决定公平

Python 标准库提供两条随机路径，用途完全不同。

| 项目 | `random`（Mersenne Twister） | `secrets`（CSPRNG） |
| --- | --- | --- |
| 底层算法 | 梅森旋转，纯算法伪随机 | 读取 `os.urandom`，操作系统熵源 |
| 可预测性 | 给定足够多的历史输出可反推内部状态 | 无内部状态可反推，输出不可预测 |
| 适用场景 | 模拟、抽样演示、游戏视觉 | 令牌生成、密码学、抽签摇号 |
| 是否适合抽奖 | 不适合 | 适合，本技能默认使用 |

梅森旋转的内部状态为 19937 位，看似庞大，但连续输出 624 个 32 位整数即可完整还原状态，之后所有输出都能被准确推算。抽签名单通常只有几十到几百人，抽取过程产生的随机数远不足以暴露状态，问题出在另一处：任何人只要拿到相同的 `sys` 状态或系统时间种子，就能复现整段抽取。以时间戳为默认种子的程序，攻击者把时间窗口缩小到秒级即可穷举。

`secrets` 模块通过 `secrets.randbelow(n)` 直接向操作系统请求随机整数，抽取者与被抽者都无法预判下一位是谁，也无法从已公布的结果反推出未公布的结果。

## 二、两种「可验证」，别混为一谈

**可复现**：给定同一个种子，同一份名单、同一套参数，能跑出完全相同的结果。适合审计、复盘、教学演示。本技能用 `--seed` 提供该模式，算法把浮点权重统一放大 `10^6` 倍并取整，规避浮点误差带来的不可复现。

**可核验**：不需要知道随机序列，也能判断这份结果与这份名单之间是否自洽、有没有被事后改动。本技能用证明文件提供该能力。

两种能力的取舍：`secrets` 模式天然不可复现（这正是它的价值），但可核验；`--seed` 模式既可持续复现也可核验，代价是种子一旦提前泄露，结果可被预判。审计场景的正确做法是抽取前公示名单哈希与承诺值、抽取后再公布种子与结果。

## 三、哈希承诺机制

抽签留痕的完整链条由三样东西构成。

1. **名单承诺**：抽取前对候选池计算 `candidates_sha256`，把哈希值公示出去。名单一旦被改动，哈希随即失效。
2. **熵摘要**：抽取过程中每次抽样使用的原始随机整数被记录成轨迹，对轨迹取 SHA256 得到 `entropy_digest`，为每一轮的随机性留下指纹。
3. **结果承诺**：对中奖名单计算 `winners_sha256`，再由「名单哈希 + 结果哈希 + 时间戳」合成 `commitment_sha256`，形成整体封印。

三者的作用是把「信任抽取者」转换为「信任数学」：复核者不必相信抽签的人说了什么，只要跑一遍校验脚本，就能判断文件是否自洽。

## 四、`verify_proof.py` 校验了哪些内容

| 序号 | 校验项 | 拦截的作弊手法 |
| --- | --- | --- |
| 1 | 证明结构标识 | 伪造或错用其他格式的证明 |
| 2 | 候选池哈希重算 | 抽取后往名单里塞人、删人 |
| 3 | 中奖名单哈希重算 | 抽取后改动结果 |
| 4 | winners 与 draws 逐项吻合 | 只改结果不改过程 |
| 5 | 索引回溯到候选池同名条目 | 结果与名单对不上 |
| 6 | 每轮熵摘要自洽 | 随机轨迹被替换 |
| 7 | 承诺值合成一致 | 时间戳或哈希被篡改 |
| 8 | 去重模式人数上限 | 去重失效导致重复中奖 |
| 9 | `--seed` 模式完整重放 | 声称可复现却复现不出来 |
| 10 | 随机轨迹逐位复现 | 种子与结果不匹配 |

退出码语义：`0` 表示全部一致，`1` 表示存在不符项，`2` 表示文件不存在或解析失败。

## 五、这套机制的边界

- 校验脚本与抽签程序同处一份代码仓库时，复核者需要独立获取脚本副本，才谈得上独立复核。
- 证明文件本身可被整体替换为一份「内部自洽的伪造证明」，反制手段是抽取前先公示名单哈希与承诺值，让事后替换对不上先前公示。
- 密码学安全随机同样不能防止「名单本身被提前替换」，候选池的真实性依赖抽取前的公示环节。
- 抽签只能解决「分给谁」的公平，解决不了「该不该分」与「分多少」的问题。
